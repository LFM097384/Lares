# 「挂着」(可约)协议

一个人同时在好几个圈子里,想找人聊但不指定跟谁 —— 于是把自己挂出去,
对选定的几个圈子可见。**第一个**来找他的人把双方拉进**那个人所在的圈子**,
此刻挂着状态立即取消,其他圈子的人不再看到他可约。

## 为什么不是「同时在多个房间里」

最直觉的实现是让一条连接同时属于多个圈子。**没有这么做**,原因是
`circleAllowed()`(`server/src/index.js`)在 circle 模式下把连接
**钉死在证明过的那一个圈子**,而那正是修过 5 个越权漏洞的地方。

这里改用另一个结构:**一个全局可约表 + 广播时按授权范围过滤**。
鉴权模型一行未动。

服务端本来就把两件事分开了:
- `lobby` —— 所有 hello 过的连接(在线)
- `session.circleId` —— 此刻在哪个房间里(单值)

「挂着」属于前者,不需要后者。

## 消息

### 客户端 → 服务器

| 消息 | 字段 | 说明 |
|---|---|---|
| `available` | `circleIds: string[]` | 挂起。只接受**自己有权进**的圈子,否则回 `auth_scope` |
| `unavailable` | — | 取消。只能取消自己的 |
| `reach` | `userId`, `circleId?` | 去找某人。不给 `circleId` 时取双方都可见的第一个 |

### 服务器 → 客户端

| 消息 | 字段 | 说明 |
|---|---|---|
| `available_ok` | `circleIds` | 挂起回执(实际生效的圈子) |
| `member_available` | `userId`, `name`, `since`, `circleIds` | 某人可约。`circleIds` **只含观察者有权看到的那几个** |
| `member_unavailable` | `userId` | 某人不再可约 |
| `reached` | `circleId`, `by`, `byUserId` | 「有人来找你了」,发给被找的人 |
| `reach_failed` | `reason` | `gone` / `auth_scope` |

## 三条不越权的防线

这是新增的一条广播通道,不过滤就等于把「某人有空」泄露给无关圈子。

1. **挂起时过滤**:`available` 只接受 `circleAllowed()` 通过的圈子 ——
   否则等于借这条消息把自己广播进一个没有口令的圈子。
2. **广播时过滤**:`member_available` 只发给对**至少一个**可见圈子有权的连接,
   且 `circleIds` 字段只列观察者有权看到的那几个 ——
   不泄露「他还挂在别的圈子」这件事。
3. **reach 时过滤**:看不见的人也找不到,且目标圈子必须双方都有权。

## 自动取消的三个时机

| 时机 | 为什么 |
|---|---|
| 进任何房间 | 人已经在房里了,再显示可约就是个点进去没反应的标记。放在 `joinCircle()` 里而不是只放在 `reach` 分支 —— 用户自己点进某个圈子时同样要取消 |
| 断线 | 否则留下幽灵。只清**这条连接**挂起的那个:同一个人在别的设备上挂着的不该被误清 |
| 显式 `unavailable` | 用户主动收回 |

## 边界情况

- **已在房间里不能挂着** —— 两者语义互斥,回 `already_in_room`
- **后连上来的人要能看到已挂着的人** —— hello 时补发,否则只有
  「挂起那一刻正好在线」的人看得到
- **同圈第三人可以进** —— A、B 聊上了,同圈的 C 不该被拦。
  这就是普通的圈子语音房,只是对**其他圈**不再显示可约

## 状态存储

纯内存、断线即消、**不落盘** —— 与 presence 同级别。
`available: Map<userId, {circleIds, name, since, ws}>`

## 跨服务器(第二步,未做)

客户端**当前只连一台服务器**(`activeProfile` 单值、`SignalingClient` 单条),
所以一个人的所有圈子本来就在同一台机器上,可约状态只需存在用户自己选的那台。

要做到「甲圈在我的服务器、乙圈在朋友的服务器,也同时可见」,走的是
**客户端聚合**:客户端同时连 N 台服务器,在**每台上各自**挂起。
服务器之间不通信、不需要跨服身份验证 —— 因为根本不存在「跨服」这回事,
你在甲服务器是甲身份,在乙服务器是乙身份,各用各的口令认证。

这样做的代价只有一个:客户端要管多条连接。而收益是**零协议变更、
零新信任假设** —— 对一个开源自托管项目,这比服务器互联(Matrix/ActivityPub 式)
现实得多,后者需要跨服身份体系、服务器发现、信任模型和抗滥用,是数月级子项目。

实现时的分层:主连接不动(仍是单条,负责进房/RTC/聊天),
另开 N 条**只做 presence** 的轻连接,收到「有人来找」就把主连接切过去。
