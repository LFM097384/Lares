# 计划：插件协议与内核边界

> 内部文档。2026-09 立项。
> 目标：把 Lares 收敛成「加密 + 语音」内核，其余能力由插件提供。

## 先回答一个问题：内核包含什么

插件化真正的设计工作不在插件 API，而在**划线**——哪些进内核，哪些出去。
线画错了，后面全是补丁。

判断标准只有一条：**如果这件事做错了，是不是会让「端到端加密」这个承诺失效？**

是 → 内核。否 → 插件。

### 内核（不可插拔）

| 能力 | 为什么必须在内核 |
|---|---|
| 身份与签名 | 插件能伪造身份，整个体系就垮了 |
| E2EE 密钥派生与持有 | 密钥一旦交给插件，插件就能把它发走 |
| 帧的加解密 | 同上 |
| 语音（LiveKit 接入） | 它和 E2EE 在同一条数据路径上 |
| 文本消息 | 最小可用产品的下限；也是插件失效时的兜底 |
| 成员与权限 | 决定谁能进、谁能发 |
| 录音知情同意 | 法律义务，不能让插件绕过 |

### 插件（可插拔）

图片、文件、视频、视频通话、位置共享、地图、语音便签、
AI bot、转录、翻译、自定义 UI 面板……

注意这个清单里有**现在已经内置的功能**（位置、便签、图片）。
它们应当逐步迁出去 —— 不是因为写得不好，而是因为
「一个功能能否用插件实现」是检验插件 API 是否够用的唯一标准。
**自己不吃狗粮的插件系统，一定是残废的。**

## 三个 Lares 特有的约束

DSH 的插件跑在本机、只影响自己。Lares 是多端实时通信，多三重约束：

### 一、插件必须两端都有 → 需要能力协商

我装了视频插件，你没装，我发的帧你解不开。
这不是报错，是**协议协商**问题。

握手时双方交换支持的帧类型：

```json
{"t":"hello","caps":["text","img","file/v1","video/v1"]}
```

发送方只发对方声明支持的类型。不支持时降级：
视频消息降级成一条「[视频] 对方的客户端没装视频插件」的文本。

⚠️ 降级必须是**发送方**做的。让接收方显示「未知消息类型」是偷懒，
用户看到的应该是一句人话。

### 二、E2EE 的边界：插件拿不到密钥

这是本设计最关键的一条。

**插件永远不接触明文密钥，也不接触加密后的字节。**
它只提交「要发什么」，内核负责加密；只收到「解密后的内容」，
不知道密钥是什么。

```
插件 →  {type: "file/v1", header: {...}, payload: <bytes>}
          ↓ 内核加密、分片、发送
        网络
          ↓ 内核接收、重组、解密
插件 ←  {type: "file/v1", header: {...}, payload: <bytes>}
```

于是「E2EE」的承诺仍然成立：**即使插件是恶意的，它也只能泄露
它自己经手的那条消息，不能泄露密钥、不能解密别人的历史。**

这比"给插件一个受限的加密 API"安全得多 —— 那种设计里，
密钥总有办法被套出来。

### 三、App Store：2.5.2 禁止下载并执行代码

⚠️ **这是硬约束，直接决定插件的分发形态。**

一个能装第三方插件的 App，在审核眼里接近「应用商店中的应用商店」，
同时踩 2.5.2（下载可执行代码）和 3.1.1（绕过 IAP）。

四种插件形态，合规性不同：

| 形态 | iOS | 说明 |
|---|---|---|
| **服务端插件** | ✅ | 跑在服务器,客户端只渲染。AI bot 属于此类 |
| **编译期插件** | ✅ | 插件是 Dart 包,用户编译自己的版本。桌面/Android 侧载 |
| **声明式插件** | ✅ | 只提供数据与 UI 描述,不执行任意代码 |
| 运行时加载代码 | ❌ | 2.5.2 明确禁止 |

**这不是妥协,是分层。** 真正需要「任意代码」的场景(bot、转录、翻译)
恰好最适合放服务端 —— 它们要跑模型、要长时在线,本来就不该在客户端。

客户端插件的定位是「渲染与交互」,那部分用声明式就够。

## 协议设计

### 现有信封已经够用

```text
[ 4 字节 大端 uint32 headerLength ]
[ headerLength 字节 UTF-8 JSON header ]
[ 余下全部字节 原始二进制 payload ]
```

`header.t` 就是天然的类型分发点，`chat_service.dart:274` 那句
`default: break; // 未知 t:忽略,不是错误` 已经是正确的向前兼容姿态。

**不需要重新设计线格式。** 要加的是三样：

### 1. 类型命名空间

现在是 `"text"` / `"img"`。插件类型必须带命名空间，避免撞车：

```
text                    内核
img                     内核（将来迁出）
x/com.example.chess     第三方，反向域名
```

`x/` 前缀让内核一眼看出「这是插件的，我不认识很正常」。

### 2. 能力协商

hello 帧带 `caps` 数组。服务端转发给同圈成员，
客户端据此决定「这条消息发不发得出去」。

### 3. 插件清单

```json
{
  "id": "com.example.chess",
  "name": "圈内象棋",
  "version": "1.0.0",
  "frameTypes": ["x/com.example.chess"],
  "permissions": ["send_frames", "render_panel"],
  "minCoreVersion": 2
}
```

`permissions` 现在只有两三项，但**必须从第一版就有** ——
将来加「读历史消息」「访问麦克风」这类敏感权限时，
才有地方声明和展示。

## 插件 API（客户端侧）

```dart
abstract class LaresPlugin {
  PluginManifest get manifest;

  /// 收到一帧属于本插件的消息。**已解密**。
  void onFrame(PluginFrame frame);

  /// 渲染一个面板。返回 null 表示本插件没有 UI。
  Widget? buildPanel(BuildContext context, PluginContext ctx);

  /// 在消息输入区加一个按钮（如「发文件」）。
  List<ComposerAction> composerActions(PluginContext ctx);
}
```

`PluginContext` 提供的能力**刻意很窄**：

```dart
abstract class PluginContext {
  /// 发一帧。内核负责加密与分片。
  Future<void> send(String type, Map<String, dynamic> header, [List<int> payload]);

  /// 当前圈子的成员（只读快照，不含任何凭据）。
  List<MemberView> get members;

  /// 本插件的私有存储。按插件 id 隔离。
  PluginStore get store;
}
```

**刻意不提供**：密钥、原始网络连接、其他插件的数据、
服务器地址与口令、文件系统的任意访问。

## 分阶段

### 第一阶段：把内核的边界立起来（不做插件加载）

1. 帧类型加命名空间
2. hello 握手带 `caps`，实现发送方降级
3. 把 `chat_service.dart` 的 switch 改成注册表
4. **把「图片」改写成第一个内置插件** —— 走完整插件 API，
   证明这套 API 真的够用

这一步做完，代码里就有了清晰的内核/外围分界，
即使插件加载永远不做，架构也更干净。

### 第二阶段：服务端插件（AI bot 是第一个）

bot 以成员身份接入，持 `role: "bot"` 证书（见
`docs/plans/identity-and-roles.md`）。这条路 iOS 完全合规。

### 第三阶段：客户端插件（桌面/Android 先行）

编译期插件：用户拿到一个插件包，自己编译一份带它的客户端。
门槛高，但对开源项目是自然的形态。

iOS 上如果要开放，只能走声明式，且需要仔细评估 2.5.2。

## 必须现在做对的

1. **命名空间从第一版就有**。`x/` 前缀加不上去的话，
   将来第三方类型和内核类型会撞。
2. **`caps` 协商从第一版就有**，哪怕现在只有两个类型。
   握手格式改起来最难。
3. **插件永远拿不到密钥**。这条一旦破例，就再也收不回来。
4. **`permissions` 字段存在**，哪怕现在是空数组。
5. **内核版本号**。`minCoreVersion` 让插件能声明依赖。

## 未决问题

- 插件的 UI 用什么渲染？直接给 `Widget` 最灵活，但那要求插件是 Dart 代码
  （编译期）。声明式（JSON 描述 UI）能上 iOS，但表达力有限。
  是否两套都做？
- 插件之间能否通信？现在倾向禁止 —— 一旦允许，权限模型会复杂一个量级。
- 服务端插件的沙箱：bot 跑在服务器上，它能看到什么？
  未加密圈子的全部内容，这个要在 UI 上讲清楚。
