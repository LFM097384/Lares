# 计划：身份与权限体系

> 内部文档。2026-09 立项。
> 起因：口令泄露后必须解散重建整个圈子；以及 AI bot 需要稳定的常驻身份。

## 要解决的三件事

1. **踢人**。一个人泄露了口令，现在只能解散圈子重建——所有人重新加好友、
   重新同步口令。社交成本极高，这是用户明确提出的主要痛点。
2. **AI bot 的稳定身份**。bot 作为常驻成员，成员变动或凭据轮换时
   **不应需要重新加入**。
3. **角色**。bot 与人应当有不同的权限边界和界面呈现。

## 结论：保留无账号，用设备密钥对 + 成员证书

「无账号」和「有身份」不矛盾。账号是某个服务商那里的注册记录；
身份只需要**可验证且不可伪造**。密码学能给出后者，不需要前者。

### 为什么现在的 userId 不够

```dart
// identity.dart 现状
userId = 'u_${DateTime.now().microsecondsSinceEpoch.toRadixString(36)}';
```

它只是个本地随机串，**完全可以伪造**——任何人都能声称自己是 `u_abc123`。
所以服务端没法"踢掉某一个人"，只能靠换口令把所有人一起挡在外面。

那个文件的注释已经预留了出口：「后续接入真实账号时只需替换本类的 load()」。

### 新模型

每台设备首次启动生成一对 **Ed25519** 密钥，私钥存进已有的 `SecretVault`
（iOS Keychain / Windows DPAPI），公钥指纹即 `userId`。

建圈者持有该圈的签名密钥，为每个成员签发一张证书：

```json
{
  "circleId": "home",
  "memberKey": "<成员公钥>",
  "role": "owner" | "member" | "bot",
  "issuedAt": 1789000000,
  "sig": "<圈主签名>"
}
```

进圈时出示证书 + 用设备私钥签服务端下发的 challenge。服务端验两件事：

1. 证书确实由该圈圈主签发
2. challenge 签名确实来自证书里那个公钥

两者都过才放行。**服务端由此精确知道进来的是谁**，这正是踢人所必需的。

### 痛点怎么被解决

| 场景 | 现在 | 之后 |
|---|---|---|
| 某人泄露凭据 | 解散重建整个圈子 | 圈主签一张吊销声明，那一个公钥出局，**其他人无感** |
| 加新人 | 传口令（可被转发） | 签一张证书给他的公钥，**只对他有效** |
| AI bot | 圈子重建就得重加 | 证书长期有效，**成员变动不影响** |

## 关键设计取舍

### 一、鉴权凭据与 E2EE 密钥解耦

现在两者是同一个东西：圈口令经 Argon2id 派生出 E2EE 密钥
（`e2ee_key.dart`）。这导致**换口令 = 换密钥 = 老成员听不见新成员**。

新模型里分开：

- **鉴权**：证书 + 签名。可以随时吊销、重签，不影响通话内容。
- **E2EE 密钥**：建圈时随机生成，加入时用对方公钥加密后分发。

于是「踢人」不再需要全员同步密钥。

⚠️ 代价：被踢的人如果**录过**旧音频，仍能解密那些。他进不来了，
但历史不会因此变得安全。真要防这个，踢人后需要主动轮换 E2EE 密钥
——那时才需要全员在线同步。**做成用户主动触发的动作，不要默认**。

### 二、圈主设备丢失

这是无账号方案的固有代价：没有服务商托管身份，恢复只能靠自己备份。

三条缓解路径，建议都做：

1. **建圈时导出恢复密钥**，引导用户存到密码管理器
2. **多管理员**：`role: "owner"` 可以有多个，任一个都能签发和吊销
3. **降级可用**：圈主丢了只是不能**签发新成员**和**踢人**，
   现有成员照常通话。不是灾难性失效。

### 三、AI bot 的私钥放在服务器上

bot 跑在服务端，它的私钥也就在服务端。这确实意味着
**拿到服务器的人可以冒充 bot**。

但这并不削弱整体：服务器本来就能看到所有未加密圈子的内容。
bot 的威胁模型不高于服务器本身。

真正要守住的是：**bot 的证书是 `role: "bot"`，权限受限**——
不能签发成员、不能踢人、在界面上明确标识。
开了 E2EE 的圈子 bot 不进（这条已是现有设计）。

## 为什么不用别的方案

### TOTP（用户提过）

本质是**共享种子**：种子人人都有，所以人人都能生成有效码，
服务端分不清谁是谁。能防「口令截图被转发」，**防不了「持有种子的人主动泄露」**。
而后者才是痛点。

可以作为第二层叠加（让日常进圈免输入），但它不解决身份问题。

### MLS（RFC 9420）

密码学上是这个问题的"正解"，但对一个人的团队太重：
树形密钥协商、成员状态同步、并发提交冲突处理。
收益主要在「前向保密」和「后妥协安全」，而我们的威胁模型里
这两项的优先级低于「能踢人」。

**不做。** 如果将来真需要，证书体系可以作为它的身份层。

### 轻量账号

能解决问题，但违背产品核心主张（隐私政策里写着「没有账号体系，
不收集手机号、邮箱」），而且引入服务商依赖。
既然密码学方案可行，**不退这一步**。

## 迁移路径

必须支持老客户端和新客户端共存一段时间。

| 阶段 | 服务端 | 客户端 |
|---|---|---|
| 1 | 同时接受「口令」和「证书」 | 新版生成密钥对，但仍用口令进圈 |
| 2 | 同上 | 新版建圈时签发证书；老圈子提供「升级」入口 |
| 3 | 口令模式标记为 deprecated，打日志 | 提示用户升级 |
| 4 | 关闭口令模式 | — |

⚠️ 自建服务器的用户可能长期不升级，第 4 步要给足过渡期，
并且在 `deploy/` 的升级说明里明确写出。

## 必须现在做对的

以下几项**以后改不动**，设计时要留够余地：

1. **证书格式带版本号**。将来加字段（过期时间、权限位）不能破坏旧证书。
2. **`role` 是开放枚举**，不是布尔。现在只有 owner/member/bot，
   将来可能有 moderator、guest。
3. **吊销列表可增长且可被验证**。服务端持有它，但每条吊销都带圈主签名
   ——这样即使服务端作恶（偷偷不吊销、或伪造吊销），客户端也能自行校验。
4. **E2EE 密钥有代次**。`{v: 1, key: "..."}`，为将来的轮换留位置。

## 可以后续迭代的

- 多管理员（先做单 owner）
- E2EE 密钥轮换（先做解耦，轮换后面加）
- TOTP 免输入（在证书之上叠加）
- 证书过期与续签

## 未决问题

- 圈子 ID 目前是用户自己起的字符串（`home`），可能冲突。
  是否改成「公钥指纹 + 人类可读别名」？这会影响邀请链接格式。
- 服务端是否需要知道成员列表？现在它只在连接时验证，不维护名册。
  维护名册便于做"谁在这个圈里"，但也让服务端知道更多。
- bot 的证书由谁签？圈主手动签一次，还是服务端自动？
