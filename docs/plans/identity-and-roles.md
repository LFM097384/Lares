# 计划：身份与权限体系

> 内部文档。2026-09 立项。
> 起因：口令泄露后必须解散重建整个圈子；以及 AI bot 需要稳定的常驻身份。

## 要解决的五件事

1. **踢人**。一个人泄露了口令，现在只能解散圈子重建——所有人重新加好友、
   重新同步口令。社交成本极高，这是用户明确提出的主要痛点。
2. **AI bot 的稳定身份**。bot 作为常驻成员，成员变动或凭据轮换时
   **不应需要重新加入**。
3. **角色**。bot 与人应当有不同的权限边界和界面呈现。
4. **跨服务器同一身份**。为将来的联合封禁留出基础。
5. **多设备**。同一个人在电脑和手机上都挂着，是这个产品的常见用法。

## 四层模型

```
① 身份层   Ed25519 主密钥对。随机生成,公钥指纹 = 全局 userId
          ↳ 不由任何服务器签发 —— 这正是它能跨服务器一致的原因
          ↳ 备份:服务器可选托管密文包 / 用户自己导出恢复码

② 设备层   主密钥签发设备证书,每台设备一把子私钥,可单独吊销
          ↳ 多设备同时在线,presence 合并显示
          ↳ 服务器可配上限(默认不限)

③ 成员层   圈主签发成员证书 {circleId, memberKey, role}
          ↳ 由圈主签,本圈有效

④ 封禁层   服务器订阅的公钥黑名单,每条带签发者与理由
          ↳ 由服务器自己决定信任哪些封禁源
```

## 结论：保留无账号，用设备密钥对 + 成员证书

「无账号」和「有身份」不矛盾。账号是某个服务商那里的注册记录；
身份只需要**可验证且不可伪造**。密码学能给出后者，不需要前者。

### ⚠️ 身份不能由服务器签发

一个容易走错的方向：「客户端告诉服务器自己是谁，服务器签发身份证书」。

这**会破坏跨服务器身份**。服务器 A 签的证书，服务器 B 凭什么认？
B 不信任 A 的签名密钥。于是又退回到现在 `presence_pool.dart` 里
那个 `'$serverId/$userId'` 的拼接——那行注释本身就是这个问题的活证据。

正确的关系是：**身份由用户自己持有，服务器只负责验证**。
服务器要 challenge，客户端用私钥签名，服务器验签。
这样 A、B、C 看到的是同一个公钥指纹，联合封禁才有基础
（黑名单里存公钥，任何服务器都能独立核对）。

服务器该签发的是**圈子成员资格**，那是本服务器的事，本地有效即可。
身份和成员资格是两层，不要合并。

### 为什么现在的 userId 不够

```dart
// identity.dart 现状
userId = 'u_${DateTime.now().microsecondsSinceEpoch.toRadixString(36)}';
```

它只是个本地随机串，**完全可以伪造**——任何人都能声称自己是 `u_abc123`。
所以服务端没法"踢掉某一个人"，只能靠换口令把所有人一起挡在外面。

那个文件的注释已经预留了出口：「后续接入真实账号时只需替换本类的 load()」。

### 新模型

每台设备首次启动生成一对 **Ed25519** 密钥，私钥存进已有的 `SecretVault`
（iOS Keychain / Windows DPAPI），公钥指纹即 `userId`。

建圈者持有该圈的签名密钥，为每个成员签发一张证书：

```json
{
  "circleId": "home",
  "memberKey": "<成员公钥>",
  "role": "owner" | "member" | "bot",
  "issuedAt": 1789000000,
  "sig": "<圈主签名>"
}
```

进圈时出示证书 + 用设备私钥签服务端下发的 challenge。服务端验两件事：

1. 证书确实由该圈圈主签发
2. challenge 签名确实来自证书里那个公钥

两者都过才放行。**服务端由此精确知道进来的是谁**，这正是踢人所必需的。

### 痛点怎么被解决

| 场景 | 现在 | 之后 |
|---|---|---|
| 某人泄露凭据 | 解散重建整个圈子 | 圈主签一张吊销声明，那一个公钥出局，**其他人无感** |
| 加新人 | 传口令（可被转发） | 签一张证书给他的公钥，**只对他有效** |
| AI bot | 圈子重建就得重加 | 证书长期有效，**成员变动不影响** |

## 身份备份与恢复

用户换设备或重装后要能找回身份。两条路都提供：

1. **本地导出**（默认引导）。导出恢复码或文件，用户自己保管。
2. **服务器托管密文包**（可选，圈主/服主决定是否开启）。
   用户设一个密码，客户端用它加密私钥后把**密文**传给服务器。
   换设备时输密码取回。体验上等同「账号密码登录」，
   但服务器**看不到私钥**，只存一团密文。

### 🚫 绝不用密码推导密钥（brainwallet）

一个看似优雅的想法：「账号 + 密码 + 服务器 ID 三个字符串推导出密钥对，
用户记住密码就能恢复」。**这条路不能走**，理由是结构性的：

**公钥是公开的，攻击者可以离线暴力破解，不联网、不受任何速率限制。**

现在的口令系统里，猜错会被服务器 4401 拒绝、被限流封禁。
但如果公钥由密码推导，攻击者拿到公钥后就能在自己机器上疯狂试：

```
猜一个密码 → 推导 → 比对公钥 → 不对就换下一个
```

一块 GPU 每秒几十万次。比特币社区实测过这个模式
（[The Bitcoin Brain Drain](https://jbonneau.com/doc/VBCKM16-FC-bitcoin_brain_wallets.pdf)）：
**绝大多数用户自选密码在几天内被破解**，且有攻击者专门蹲守，资金秒级被转走。

即便用 Argon2id 拖慢到每秒几千次也救不回来 —— 用户会选
「名字+生日」这种密码，那个空间小到几小时就穷尽。

第二个问题：**这种身份改不了密码**。密码变了公钥就变了，等于换了个人，
所有圈子的成员证书全部作废。

### 对比

| | 密码推导（brainwallet） | 密码加密备份 |
|---|---|---|
| 能离线爆破吗 | ✅ 拿到公钥就能 | ❌ **必须先偷到密文包** |
| 能改密码吗 | ❌ 改了就换身份 | ✅ 重新加密一次，身份不变 |
| 密码弱的后果 | 身份直接丢 | 只有拿到密文包的人能试 |

差别看着小，实际是把攻击面从**全世界**缩到**能拿到你备份文件的人**。

具体算法：Argon2id（参数复用 `e2ee_key.dart` 的实测取值）
派生对称密钥 → XChaCha20-Poly1305 加密私钥。

## 关键设计取舍

### 一、鉴权凭据与 E2EE 密钥解耦

现在两者是同一个东西：圈口令经 Argon2id 派生出 E2EE 密钥
（`e2ee_key.dart`）。这导致**换口令 = 换密钥 = 老成员听不见新成员**。

新模型里分开：

- **鉴权**：证书 + 签名。可以随时吊销、重签，不影响通话内容。
- **E2EE 密钥**：建圈时随机生成，加入时用对方公钥加密后分发。

于是「踢人」不再需要全员同步密钥。

⚠️ 代价：被踢的人如果**录过**旧音频，仍能解密那些。他进不来了，
但历史不会因此变得安全。真要防这个，踢人后需要主动轮换 E2EE 密钥
——那时才需要全员在线同步。**做成用户主动触发的动作，不要默认**。

### 二、圈主设备丢失

这是无账号方案的固有代价：没有服务商托管身份，恢复只能靠自己备份。

三条缓解路径，建议都做：

1. **建圈时导出恢复密钥**，引导用户存到密码管理器
2. **多管理员**：`role: "owner"` 可以有多个，任一个都能签发和吊销
3. **降级可用**：圈主丢了只是不能**签发新成员**和**踢人**，
   现有成员照常通话。不是灾难性失效。

### 三、AI bot 的私钥放在服务器上

bot 跑在服务端，它的私钥也就在服务端。这确实意味着
**拿到服务器的人可以冒充 bot**。

但这并不削弱整体：服务器本来就能看到所有未加密圈子的内容。
bot 的威胁模型不高于服务器本身。

真正要守住的是：**bot 的证书是 `role: "bot"`，权限受限**——
不能签发成员、不能踢人、在界面上明确标识。
开了 E2EE 的圈子 bot 不进（这条已是现有设计）。

## 为什么不用别的方案

### TOTP（用户提过）

本质是**共享种子**：种子人人都有，所以人人都能生成有效码，
服务端分不清谁是谁。能防「口令截图被转发」，**防不了「持有种子的人主动泄露」**。
而后者才是痛点。

可以作为第二层叠加（让日常进圈免输入），但它不解决身份问题。

### MLS（RFC 9420）

密码学上是这个问题的"正解"，但对一个人的团队太重：
树形密钥协商、成员状态同步、并发提交冲突处理。
收益主要在「前向保密」和「后妥协安全」，而我们的威胁模型里
这两项的优先级低于「能踢人」。

**不做。** 如果将来真需要，证书体系可以作为它的身份层。

### 轻量账号

能解决问题，但违背产品核心主张（隐私政策里写着「没有账号体系，
不收集手机号、邮箱」），而且引入服务商依赖。
既然密码学方案可行，**不退这一步**。

## 迁移路径

必须支持老客户端和新客户端共存一段时间。

| 阶段 | 服务端 | 客户端 |
|---|---|---|
| 1 | 同时接受「口令」和「证书」 | 新版生成密钥对，但仍用口令进圈 |
| 2 | 同上 | 新版建圈时签发证书；老圈子提供「升级」入口 |
| 3 | 口令模式标记为 deprecated，打日志 | 提示用户升级 |
| 4 | 关闭口令模式 | — |

⚠️ 自建服务器的用户可能长期不升级，第 4 步要给足过渡期，
并且在 `deploy/` 的升级说明里明确写出。

## 必须现在做对的

以下几项**以后改不动**，设计时要留够余地：

1. **证书格式带版本号**。将来加字段（过期时间、权限位）不能破坏旧证书。
2. **`role` 是开放枚举**，不是布尔。现在只有 owner/member/bot，
   将来可能有 moderator、guest。
3. **吊销列表可增长且可被验证**。服务端持有它，但每条吊销都带圈主签名
   ——这样即使服务端作恶（偷偷不吊销、或伪造吊销），客户端也能自行校验。
4. **E2EE 密钥有代次**。`{v: 1, key: "..."}`，为将来的轮换留位置。
5. **身份层与服务器无关**。userId 永远是主公钥指纹，绝不拼 serverId。
   一旦某处代码依赖了「身份属于某台服务器」，跨服务器封禁就废了。
   现有的 `presence_pool.dart` 的 `'$serverId/$userId'` 是这次要消除的。
6. **主密钥与设备密钥分离**，哪怕第一版只有一台设备。
   把「设备证书」这层先立起来，将来加设备才不用改身份格式。
7. **圈子 ID 是公钥指纹**，不是用户起的名字。
   `c_7f3a9c2e...` 全局唯一，别名只是显示用。
   邀请链接形如 `lares://circle/c_7f3a9c2e...?name=家人`。
   圈子本身有密钥对，圈主签成员证书用的正是它。

## 可以后续迭代的

- 多管理员（先做单 owner）
- E2EE 密钥轮换（先做解耦，轮换后面加）
- TOTP 免输入（在证书之上叠加）
- 证书过期与续签
