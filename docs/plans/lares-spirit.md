# 计划:AI 炉灵(第四项 —— 列入计划,先不做)

> 状态:**未开工**。本文记录已经想清楚的架构决定,免得将来重新推一遍。
> 写于 2026-09-14。

## 一句话

让「炉灵」成为圈子里一个**有独特身份的用户** —— 它在成员列表里可见,
有自己的头像和状态,能被邀请进圈,也能被请出去。

## 核心架构决定:炉灵是参与者,不是服务器

这条是整份计划的地基,来自一次关键讨论。

最初的表述是「E2EE 开了就只能在本地跑 AI」,这个说法**不准确**。
LiveKit 官方文档原话:

> "A LiveKit agent is **just another participant in the room**, so it needs
> the shared encryption key to publish and subscribe to encrypted media."
> —— <https://docs.livekit.io/transport/encryption/agents.md>

`@livekit/rtc-node` 带 `E2EEOptions`,bot 拿到同一把共享密钥就能解密入站音频、
加密出站 TTS。所以 **E2EE 与 AI 炉灵并不互斥**。

但有一个必须守住的边界:

> ⚠️ **不能让服务器"自动接入"** —— 那等于服务器持有密钥,E2EE 就白做了。

密钥由**圈子口令派生**,而口令只有圈成员知道。所以炉灵要进圈,
必须有人**主动邀请它并把口令给它**。

| | 服务器自动接入 | 被邀请的参与者(选这个) |
|---|---|---|
| 密钥归属 | 服务器持有 → E2EE 失效 | 圈成员显式授权 |
| 用户感知 | 不知道有人在听 | 成员列表里明确可见 |
| 可撤销 | 不能 | 踢出去即可 |
| Guideline 1.2 | 隐形监听,不满足「知情」 | 可见参与者,天然满足 |

最后一行是意外收获:这个模型顺带解决了合规问题。

## 与需求⑧(录音/STT)的关系

炉灵天然需要 STT。但**不要复用** `_disabled/recording_stt/` 那条路:
那是客户端本地离线识别(sherpa-onnx),为「谁说了什么」的聊天记录设计的。
炉灵的 STT 应该跑在 bot 侧,和它的 LLM、TTS 在同一个进程里。

## 已定的产品决策(2026-09-14)

### 1. 唤醒方式:语音唤醒词「炉灵」

像 Siri 一样喊名字唤醒。技术上需要**持续监听**才能听到唤醒词。

这一点之所以可接受,是因为它与下面第 3 条**叠加后自洽**:
炉灵本来就在房间里为了做记录而听着,唤醒词不额外扩大监听面。
若将来改成按键唤醒,反而要重新论证"它平时在不在听"。

选型倾向 **openWakeWord** 一类开源本地检测:唤醒词识别在
炉灵进程内完成,不外发。

### 2. 只在**不开 E2EE** 的圈子里工作

开了 E2EE 的圈子,炉灵不进,也不记录。这条是硬边界。
(技术上炉灵拿到口令也能解密 —— 见上文;但产品上选择不这么做,
把"要不要让它听"的开关交给圈子。)

### 3. 转写记录:**炉灵自己转写、自己存**

不是服务器落盘,也不是客户端上传。炉灵作为**房间参与者**,
听到什么记什么。

为什么这个归属最重要:

| 模型 | 语义 | 知情 |
|---|---|---|
| 服务器存 | 服务器在偷偷录你们 | 需要额外告知机制 |
| 客户端存 | 各存各的,跨设备不一致 | 尚可 |
| **炉灵存** | **它在场,所以它记得** | **成员列表里看得见它** |

第三种在伦理上最站得住:用户看到炉灵在成员列表里,就知道它在听。
这与既有的录音同意协议(`recording_consent.dart` 的核心约束
「绝不采集房间不知情的音频」)是同一个原则的延伸。

### 4. 与 App Store 的排期冲突:先上架,录音功能放第二版

本轮刚把录音代码从包里彻底剔除(-21.4MB、符号归零),理由是
2.3.1 dormant features。常态化转写要把它加回来。

**决定:不在首次提审时带这个功能。** 首次审核最危险 ——
被拒会留记录且重提更严。录音+转写是隐私敏感功能,首版带着它
会显著抬高审核难度(隐私标签要加 Audio Data + 转写文本)。
上架后发版本更新,风险小得多。

### 5. 保留策略:文字永久,语音不永久

| | 保留 | 理由 |
|---|---|---|
| **转写文字** | **永久** | 它是圈子的记忆 —— 这正是炉灵的价值 |
| **原始语音** | **不永久** | 转写完即可丢弃 |

这个区分不是妥协,是**刻意的设计**:

- **体积差了三个数量级**。一小时语音约 30MB(Opus),转写文字不到 30KB。
  常驻语音房一天十几小时,只存文字才可能真的"永久"。
- **风险面完全不同**。语音里有声纹、情绪、环境音、口误、背景里别人的话;
  文字只留下说了什么。永久保留语音是一种远大于其价值的风险敞口。
- **它让"永久"这个承诺可兑现**。如果两者都永久,磁盘会先扛不住,
  最终结果是两者都保不住。

工程含义:
- 语音只在**转写管线内**短暂存在,转写完立即删,不落长期盘
- 需要一个明确的临时区 + 失败兜底(转写失败的音频也要有过期清理,
  不能因为"还没转写成功"就无限堆积 —— 现成的 `disk_guard.dart` 有
  相关经验,注意它那个「死区」的坑:阈值 90% 阻塞写入但清理只在 100% 以上
  触发,会永久卡死)
- 转写文字要能**搜索**,否则"永久保留"没有意义
