## 1. 发现

### A. 证据与评测

**F1 · blocker · §1 L28；§6.4 L366-376；§6.7 L438-441；§11.2 L711：引用的评测结果已不存在，而且数字不稳定**

- **证据**：
  - `server/chatham/eval/results.md` 现在的内容是 `Run: 2026-10-18T01:41:33.721Z`，`Mode: MOCK — offline heuristics, NOT LLM numbers`，并写明 "Do not quote as LLM results"。
  - L13-19 现在是 MOCK 表：raw 42.4，+L4 22.0，random 20.0。
  - 设计文档引用的 "97.5% → 70–75%" 在仓库里**已无出处**。
  - 本次评审期间还见过另一轮 LLM 结果（01:37:01，deepseek-flash）：L0+L1 72.0、+L2 78.8、+L3 72.0、+L4 68.6、ideas-only 68.6。它与 §6.4 表格的 70.3 / 76.3 / 69.5 / 74.5 **逐项不同**，最大差约 6pp。
  - 样本量：7 份 × 约 8.5 个观点，约 60 个观点；攻击采样 2 次。按二项分布估计，95% CI 约 ±11pp。§6.4 L380 说 "+L4 与 +L3 在噪声内"，这一点没错；但正因如此，表里任何两行之间的差都不可解读。
- **更要紧的一点**：ideas-only（不经任何 Gate 措辞、只给观点）的攻击准确率是 68.6%，与 +L4 持平。可见在 K2 下，Gate 的边际价值约为 0；"字面泄露压到接近 0"并不转化为归属保护。§6.4 已经承认"观点暴露角色"，却没有把这个对照列出来。
- **修复**：
  1. 把 LLM 运行结果单独提交为 `eval/results-llm-<date>.md`，在文中按 commit hash 引用。MOCK 跑数一律写到另一个文件，以后不得覆盖。
  2. 每个数字报 n 和 95% CI，并列出 ideas-only 行作为天花板对照。
  3. 删掉 "数字会随重跑变化，以该文件为准"（L376）这种无法审计的写法。

**F2 · blocker · §9.5 L654-656 对照 `4_gate_dark.png`：概念图正好用 MOCK 数字，并写死"≈随机"**

- **证据**：
  - `4_gate_dark.png` 的归属风险卡显示「✓ ≈ 随机」「22%」「随机 1/5 = 20%」。22% 恰好是 MOCK 表里的 +L4 值。
  - 设计文档的 D3（L392）和 L656 都**明令禁止**写死"≈随机"；§11.1 L703 也禁止引用 MOCK 数字。
  - 按真实的 LLM 数字，这一格应该显示约 70%，而且是红色。
- **修复**：重画 `4_gate`。显示 K1 和 K2 两个实测值，并同时给出 CI。当 K2 远高于 1/n 时，默认显示红色，配文「知道名单的人大概率能认出」。在实测数据出来之前，**不要**拿这张图做对外宣传。

**F3 · major · §6.3 L362；§6.4 D2 L391；§11.4：`roleRisk` 由一个弱模型在 convener 机器上自评，会系统性低估风险**

- **证据**：
  - 产品路径下，L4 攻击者用的是本机 Qwen3-1.7B 或 4B（L299、L362），而现实中的对手是前沿模型加 web 搜索（[RES] L150、L160-163）。弱攻击者给出的低 `roleRisk` 会让当事人误以为安全。
  - 1.7B Q8 在手机上解码约 8 tok/s（[RES] L110）。LLM 评测一轮约 90k tokens（7 份），折合每份约 13k；L3 加两轮 L4 在手机上要跑几十分钟，而 §9.6 只给自述卡留了 10 分钟窗口。
  - `roleRisk` 是 convener 本机算的，其他人无从复核。
- **修复**：
  - UI 上把 `roleRisk` 定义为**下界**，文案写「至少这么容易被认出」。
  - 在 K2 下，对所有带角色观点默认标黄，不依赖模型分数。
  - 在评测里加一个「弱攻击者与强攻击者差距」实验：本机模型对 deepseek，报告低估幅度。
  - 把 Gate 的端上耗时列为 P2 验收指标。

**F4 · major · §11.3 L720；§11.4 L726：在 ASR 文本上，"直接标识泄露 = 0" 不可达**

- **证据**：
  - sherpa 的 CER 总体是 16.8%，其中中英混杂 23.5%、英文 43.9%，而且测的还是 TTS 合成音频（[ARCH] Phase-0 表）。
  - 名单拒绝表（L1）做的是字面匹配。人名被识别成同音字或错字之后，就会**漏过 L1**，然后原样进入 L3。LLM 可能把它当作普通词保留，也可能"纠正"回真名。
- **修复**：
  - L1 加拼音或同音、编辑距离的模糊匹配。
  - 把「ASR 错误下的直接标识泄露」作为**单独**的验收行。
  - 在测到真人 CER 之前，P2 门槛只适用于手打或高质量 ASR 的文本。

### B. 密码学与协议

**F5 · blocker · §8.3 L557-567：成员公钥经口令派生的密钥交换，可被 MITM；convener 是单点信任**

- **证据**：
  - `pk_x_i` 放在 roster 帧里交换，roster 帧用 `K_circle` 加密（L560）。`K_circle` = Argon2id(passcode)（L557）。
  - 持有口令的人可以伪造 roster 帧，把自己的公钥替换成某个成员的公钥，从而拿到 `seed_s` 和所有后续的 `epochSecret`。持有口令的人包括：被踢者（[ARCH] L148、L481 写明踢人不换钥），以及 env 圈子的运营者（[ARCH] L37，env 口令是明文）。
  - 这样一来，L567 用来论证"为什么要内层密钥"的那个对手（被踢的口令持有者）**恰好能攻破**内层密钥。
  - convener 一人生成并封装所有密钥（L558、L564），可以静默给"幽灵成员"封装一份，也可以对不同成员分发不同纪元。§8.3 L569 承认"convener 是单点"，但没有把后果写进 §3 威胁模型。
- **修复**：
  1. 每台设备持有长期身份密钥（Ed25519 / X25519），用它签名本场的会话临时公钥。
  2. 会话开始时，全员核对 `rosterCommit` 的 6 字短码，与 `sealHash` 短码一起口头确认（§9.2 已有这个机制，扩展即可）。
  3. 客户端交叉校验 roster 成员数与 LiveKit 参与者数，不一致就标红。
  4. §3.4 增加一条："convener 和口令持有者可以冒充成员，直到 P3 MLS 上线"。
  5. 在 P1 之前，不得宣称"被踢者被排除"。

**F6 · blocker · §6.5 L395-421：k-of-n 放行可以被 Sybil 攻破，名单完整性取决于 convener 和服务器是否诚实**

- **证据**：
  - `rosterCommit` 是全部 `pk_i` 的 Merkle 根，"在 `chatham_opened` 时公布"（L417）。公钥经由服务器信令汇总。服务器或 convener 塞进 k−1 把自己控制的公钥，convener 就能独自凑够 k 个签名。
  - 外部验证者"无法把公钥对应到人"（L418）。这在设计上是优点，但也意味着外部**无法发现**幽灵签名人。
  - 所以 §10 L684 标的「放行摘要确实经过 k 人同意 ✅」只成立于"名单诚实"这一前提。
  - 另外，L397 写 n "不含 AI，也不含安全员"，却没说 convener 本人算不算 n。convener 运行 Gate、设定 k，又自己签名。
- **修复**：
  - 同 F5：做短码核对，并且由每位成员签署 `rosterCommit`，即 `rosterAck`。
  - `release.json` 必须附带 ≥k 个 `rosterAck`，否则验证器只显示 ◐。
  - §10 那一行降为 ◐，文案写「k 把会话密钥签了名；它们属于真实不同的人，前提是室内核对过名单」。

**F7 · major · §8.1 L529-531（`review`、`sign` 帧）；§6.5 L421（否决）：只有 release 签名有域分离，其他审批消息可以重放**

- **证据**：
  - release 签名本身绑定得很好：L404 覆盖 `sid‖draftHash‖k‖n‖rosterCommit`。
  - 但 `review` 帧（L529）和否决消息（L421）只写了"附上一个签名"，**没有规定签名覆盖哪些内容**。缺 `sid`、`segIdx`、`draftHash`、`claimId`、`round`、nonce，旧草稿上的否决或保留就能被重放到新草稿上。
  - 否决人身份靠 Merkle 证明保证，但"任何成员都能否决任何 claim"，这与 L391「被高概率指向的那个人拥有单方否决权」不一致：系统无法验证否决者是不是被指向的人，因为谁被指向只有 convener 的 L4 知道。
- **修复**：
  - 所有签名统一使用 `ctx = "lares-ch-<type>-v1"‖sid‖segIdx‖draftHash‖round‖claimId`。
  - 明确否决权的语义：要么任何人都可以否决（这更简单，也更符合"当事人不必暴露自己"），要么只有被指向的人可以否决（这就要求 convener 把指向结果用对应 `pk_i` 加密后单独下发）。

**F8 · major · §8.5 L583-599；§6.6 L430；`6_end_dark.png`：回执链证明不了声称的东西，反而会泄露你在哪个圈子**

- **证据**：
  - 回执链的事件由各方自报（ack_count、officer_action、shred），哈希链只证明**同一份日志前后一致**，不证明事件真实发生。
  - "服务器无法伪造，因为 head 由所有客户端对账"（L595）有两个问题：
    - 并非每个客户端都看得到 `officer_action`（它在 `K_safety` 下），所以各方算出的 head 本来就不一样；
    - 对账本身也走服务器信令。
  - `r_0` 包含 `cidHash`（L588）。自述卡附上 `r_0` 和 head 之后（L599、L430），要验证它就必须给出 `cidHash`。圈子 id 形如 `c_…`，空间可枚举，所以 cidHash 可以穷举。再拿去和服务器保存的 `(cidHash, sid, head)` 比对，就能把自述卡对应到具体圈子，进而推出共同在场者。这正是规则禁止的 "nor that of any other participant"。
  - `6_end_dark.png` 写「销毁回执 · 6/6 台设备已签」「烧掉的…6 台设备的内存」，暗示能证明**他人**已经销毁。这与 §10 L686 的 ❌ 和 L667「无法从这里证明」直接冲突。
- **修复**：
  - `r_0` 改用 `H(sid‖salt_s)`，其中 `salt_s` 只在室内分发，不放 cidHash。服务器只存 `H(head)`。
  - 自述卡默认**不附**回执；若要附，就附一个与圈子无关的证明。
  - `6_end` 改为「本设备已销毁 · 其他 5 台自报已销毁（无法验证）」，删掉「6/6 已签」。
  - 文中把回执改称"本机事件日志"，不叫 receipt 或 proof。

**F9 · major · §8.1 L278、L501-535；[ARCH] L512-514：15 KB 包长限制只照顾了 `utt`**

- **证据**：
  - `utt` 限制在 ≤6 KB（L278），没有问题。
  - 但 `ch.draft{draftHash, claims[], roleRisk[]}`（L401）在 1 小时会议上很容易超过 15 000 B，`roster` 帧对 12 人以上的会也一样。而 `publishData` 不做长度检查（[ARCH] L512-514），超长会静默失败，或者截断。
- **修复**：为 `ch.draft`、`ch.roster`、`ch.release` 规定分片格式，带 `{chunk i/n, hash}`，在接收端重组并校验。另外加一个集成测试：40 条 claim、12 人名单。

**F10 · major · §5.2 L270：A 档的 ack 门控只在客户端执行**

- **证据**：未 ack 的人"保持静音、听不到声音（客户端不订阅远端音轨）"。改过的客户端可以不 ack 就订阅。服务器签发的 LiveKit token（`index.js:822-833`）在会话期间权限不变。
- **修复**：
  - 服务器在收到 `chatham_ack` 之前，用 LiveKit `UpdateParticipant` 把该参与者设成 `canSubscribe=false`，收到之后再放开。
  - 文案把"点击之前听不到"改为"服务器在你确认之前不向你转发音频"。

### C. 过度宣称

**F11 · blocker · §1 L24；§4.1 T0/T1 L156-157；§4.2 L165；§10 L680：「服务器与第三方收不到任何会话内容」对 env 圈子不成立，T0 也无法验证**

- **证据**：
  - env 圈子的口令以明文放在服务器环境变量里（[ARCH] L37）。运营者可以派生出 LiveKit 共享密钥，自己签发一张 token（服务器本来就负责签发，`index.js:822`），以隐身参与者的身份入会，听到全部音频。
  - legacy 或 null 策略的圈子不走 `=== true` 门控（[ARCH] L131）。
  - T0「没有任何机器把内容转成可存储的形式」写的是 **P0 ✅**，验证方式是"看 UI 状态"。但任何参与者都可以用另一台设备、系统级实时字幕（见 F14）或 loopback 录音来采集内容。
- **修复**：
  - §5.2 的开会检查加一条硬条件：圈子必须是 `e2ee===true`，而且**不是 env 圈子**，口令只在客户端。
  - T0 改为 ◐，表述为「Lares 自身不采集；参与者设备上的其他软件无法排除」。
  - L24 改为「Lares 服务器不接收、也无法解密会话内容（非 env 的 E2EE 圈子）」。

**F12 · blocker · §2 L114、L130；§3.4 L138；§7 L463；§6.2 L344-345：「安全员协议上不能发布」「门槛未到什么都不会离开」不成立**

  - L344「没有 k 个签名…客户端拒绝展示和分享」只约束 Lares 客户端，管不住剪贴板和截屏。
  - `5_consensus_dark.png` 写「门槛未到之前，什么都不会离开这间屋子」。
  - [ARCH] L442 的 mock 文案「可看原文，不能发布」也是同样的问题。
- **修复**：
  - 全文把这类说法统一改为「**不能以 Lares 的名义放行**；和任何在场者一样，可以私下泄露」。
  - `5_consensus` 改为「门槛未到之前，Lares 不会把稿子发出去」。
  - §3.4 L138 删掉"协议能保证不能单方面发布"。

**F13 · major · `3_ai_dark.png`「不留痕」、`2_room_dark.png`「端到端点对点交换 · 不落盘 · 不上云」、`6_end_dark.png`「说过的话留在这间屋子里了」、`gate.mjs:8` "no attribution"：UI 与代码里的绝对化措辞**

**F14 · major · §3.4 L136；§5.3；§9.2 L632；`7_strict_room_dark.png`「截屏·录屏 已拦截」、`1b`「禁截屏」：防截屏防错了对象**

- **证据**：
  - A 档**只有音频**（L240，只允许麦克风）。真正需要保护的是**声音**，而 CaptureGuard 全部针对屏幕：
    - Windows 上 `WDA_EXCLUDEFROMCAPTURE`、macOS 上 `sharingType=.none` 挡不住 WASAPI loopback 或 BlackHole 一类的音频录制；
    - Android 的 `FLAG_SECURE` 挡不住系统 Live Caption，也挡不住无障碍服务读屏；
    - iOS 只能检测（L136 自己也写了）；
    - Web 只能提示（L256）。
  - 所以 `7_strict_room` 给出的「已拦截」，在 iOS、桌面和 Web 上都是错的，在 Android 上也只对画面成立。
- **修复**：

### G. 缺失项

**F24 · blocker · 整篇缺：违法内容和法律义务（CSAM、网信法规、法律保全）**

- **证据**：
  - 全文没有出现 CSAM、未成年人、PIPL、GDPR、法律保全（legal hold）这些词。§13.2 第 7 条只是一笔带过。
  - 在中国大陆，群组或音视频服务的提供者可能负有日志留存和处置义务。例如《互联网群组信息服务管理规定》要求日志保存不少于 6 个月；具体适用需要法务确认。这与"服务器不收内容"存在结构性冲突。
  - 收到法院或监管的保全令时，事件包（§7）就成了唯一的原文副本，持有人是安全员个人。
  - 聊天输入框在会话期间仍然存在（L175），会话期间能否发图片、文件，§5.3 没有说明。
- **修复**：新增 §7.6「法律与违法内容」，包括：
  - 会话期间禁止发送图片和文件，只允许音频；
  - 保全请求的处理流程：Lares 侧没有内容可交，事件包归安全员个人，要写入用户协议；
  - 法务评估：中国大陆是否需要关闭 B 档或安全员功能；
  - 未成年人：会话功能仅限 18 岁以上，至少不对 14 岁以下开放（PIPL 第 31 条）；

**F25 · major · §7 与 §5.3 第 18 项：A 档没有任何处理骚扰的路径**

## 2. 结论

**结论：方向可取，但不能按原样实现，也不能用现有文案或概念图做百年首发。**

A 档的核心思路是对的：服务器强制关闭各条路径，没有 AI，没有转写。但它的几个关键宣称存在问题：
- 「服务器收不到任何内容」对 env 和 legacy 圈子不成立（F11）；
- 「防截屏」防错了对象，A 档的资产是音频（F14）；
- 「分段」违反规则"不得来回切换"（F18）。

B 档的问题更深：
- 密钥分发和 k-of-n 的完整性最终取决于 convener 和服务器的诚实（F5、F6）；
- 安全员是一个未被承认的留存和泄露通道（F12、F15）；
- Gate 的唯一实测依据已经被 MOCK 覆盖，而且在 K2 下与"只给观点"不相上下（F1）。

设计文档在 §3.4 和 §10 的自我批评写得不错，可是 §1、§2 和概念图里的措辞没有跟上这些自我批评。

### 必须先改的 5 项

1. **F1 + F2**：把 LLM 评测结果固化为独立文件，报告 n、CI 和 ideas-only 对照；重画 `4_gate`，去掉「≈随机 22%」。
2. **F5 + F6**：加入长期身份密钥签名的会话公钥，室内口头核对 `rosterCommit` 短码，用 `rosterAck` 门控 release。在此之前，删除"被踢者被排除"和"k 人同意 ✅"的说法。
3. **F18**：把一场会限制为单向、单次转换，多段改为多场独立会话；统一正文与概念图。
4. **F11 + F12 + F13 + F14**：清理过度宣称。禁止 env 圈子开会；统一安全员文案为"不能以 Lares 名义放行"；删除「不留痕 / 点对点 / 已拦截 / 6/6 已签 / no attribution」；画面和声音的保护能力分开展示。
5. **F15 + F24**：安全员事件包改成至少两名非 convener 参与者同意才能冻结，并写入 T3 例外；新增法律与违法内容一节，覆盖 CSAM、未成年人、法律保全、PIPL/GDPR，会话期间禁止发图片和文件。
